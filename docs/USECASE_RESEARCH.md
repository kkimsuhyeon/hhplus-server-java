## 1. 명세 원문 (요약 아님, 그대로 옮김)

### Description
- 대기열 시스템을 구축하고, **예약 서비스는 작업가능한 유저만** 수행할 수 있도록 해야 한다.
- 사용자는 좌석예약 시에 **미리 충전한 잔액**을 이용한다.
- 좌석 예약 요청시에, **결제가 이루어지지 않더라도 일정 시간동안 다른 유저가 해당 좌석에 접근할 수 없도록** 한다.

### Requirements
- 5가지 API를 구현한다.
- 각 기능 및 제약사항에 대해 **단위 테스트를 반드시 하나 이상** 작성한다.
- **다수의 인스턴스로 어플리케이션이 동작하더라도 기능에 문제가 없도록** 작성한다.
- 동시성 이슈를 고려하여 구현한다.
- 대기열 개념을 고려해 구현한다.

### API Specs

| # | API | 명세 문장 |
|---|---|---|
| 1️⃣ 필수 | 예약 가능 날짜 / 좌석 조회 | 예약 가능한 **날짜 목록**을 조회할 수 있다. **날짜 정보를 입력받아** 예약가능한 좌석정보를 조회할 수 있다. 좌석 정보는 **1~50 좌석번호**로 관리된다. |
| 2️⃣ 필수 | 좌석 예약 요청 | **날짜와 좌석 정보**를 입력받아 좌석을 예약 처리한다. 예약과 동시에 해당 좌석은 그 유저에게 **약 5분간 임시 배정**된다(시간은 정책에 따라 자율). 배정 시간 내 결제가 완료되지 않으면 **임시 배정은 해제**되어야 하고 다른 사용자가 예약할 수 있어야 한다. |
| 3️⃣ 필수 | 포인트 충전 / 조회 | 사용자 식별자 및 충전할 금액을 받아 포인트를 충전한다. 사용자 식별자로 포인트를 조회한다. |
| 4️⃣ 필수 | 결제 | 결제 처리하고 **결제 내역을 생성**한다. 결제가 완료되면 해당 좌석의 **소유권을 유저에게 배정**하고 **대기열 토큰을 만료**시킨다. |
| 5️⃣ 선택 | 유저 대기열 토큰 | 토큰은 유저의 **UUID**와 대기열 관리 정보(**대기 순서 or 잔여 시간** 등)를 포함한다. **이후 모든 API는 이 토큰으로 대기열 검증을 통과해야** 이용 가능하다. 폴링으로 본인 대기열을 확인한다고 가정. → 토큰 발급 API + **대기번호 조회 API** |
| 6️⃣ 선택 | 대기열 고도화 | 예: 특정 시간 동안 N명에게만 권한 부여 / 한번에 활성화된 최대 유저를 N으로 유지 |

### KEY POINT
- 유저간 대기열을 **요청 순서대로 정확하게** 제공할 방법을 고민한다.
- 동시에 여러 사용자가 예약 요청했을 때 **좌석이 중복으로 배정되지 않도록** 한다.

## 2. 명세 문장에서 바로 뽑히는 것

### 명사 → 리소스 후보

| 리소스 | 근거 문장 | 가지고 있어야 할 정보 |
|---|---|---|
| 유저 | "사용자 식별자" | 식별자, **잔액** |
| 콘서트 일정(날짜) | "예약 가능한 날짜 목록" | 날짜, 예약 가능 여부 |
| 좌석 | "1~50 좌석번호", "날짜의 좌석" | 어느 날짜의, **좌석번호**, 상태, 가격, 임시배정 대상자, 배정 만료시각 |
| 예약 | "좌석을 예약 처리" | 유저, 좌석, 상태, 만료시각 |
| 결제 내역 | "결제 내역을 생성" | 금액, 대상, 상태, 시각 |
| 대기열 토큰 | "UUID + 대기 순서 or 잔여 시간" | UUID, 유저, 상태, **대기 순서**, 만료시각 |

| ID | 유스케이스 | 액터 | 근거 |

## 3. 명세가 말하지 않는 것 = 우리가 정해야 할 정책

명세는 일부러 비워둔 곳이 많다. **여기를 정하는 게 설계다.**

### P-1. 임시 배정 시간
"약 5분간 (시간은 정책에 따라 자율)" → 몇 분으로? 그리고 **어디에 기록**하나 — 좌석에? 예약에? 둘 다면 누가 진짜인가?

### P-2. "작업 가능한 유저"의 정의 (R1)
토큰이 ACTIVE면 되는가? ACTIVE 유저 수 상한은? 활성 유지 시간은?

### P-3. 대기열 순서 보장 방법 (R7 + R9)
요청 순서를 무엇으로 판단하나 — 발급 시각? 순번 채번? 다중 인스턴스에서 시각은 서버마다 어긋난다.

### P-4. 좌석 중복 배정 방지 방법 (R8 + R9)
DB 락? 조건부 UPDATE? 유니크 제약? 어느 것이 **여러 인스턴스에서도** 성립하나?

### P-5. 임시 배정 해제 트리거 (R4)
- (a) 스케줄러가 주기적으로 훑는다
- (b) 조회 시점에 만료된 것을 걸러낸다 (lazy)
- (c) 둘 다

각각 "해제 직후 다른 유저가 예약 가능"까지 걸리는 지연이 다르다.

### P-6. 결제 실패/취소
잔액 부족이면? 이미 결제된 예약을 또 결제하면? 만료된 예약을 결제하면?
→ 각각 **어떤 에러**로, **그때까지 바뀐 상태는 어떻게** 되나?

### P-7. 결제 단계의 원자성 (R2 + R5 + R6)
잔액 차감 / 좌석 소유권 배정 / 결제 내역 생성 / 토큰 만료 — 4가지가 한 덩어리인가? 하나가 실패하면 나머지는?

### P-8. 취소·만료된 예약 이력
지웠다가 다시 예약 가능해야 하나, 이력으로 남기나?

### P-9. 좌석번호 1~50
좌석은 날짜별로 미리 50개 만들어 두나, 예약 시점에 생성하나? 가격은 좌석마다 다른가?

### P-10. 다중 인스턴스 (R9)
대기열 상태를 **서버 메모리**에 두면 R7·R9가 즉시 깨진다. 어디에 둘 것인가?
→ 이 결정 하나가 STEP06(Redis) 진입 지점과 직결된다.

## 4. 상태 흐름 — 명세 문장에서 유도되는 뼈대

명세가 요구하는 **최소한의** 상태만 적었다. 이름과 추가 상태는 직접 정하면 된다.

```
[좌석]
  예약가능 ──(UC-7 예약요청)──> 임시배정 ──(UC-8 결제완료)──> 소유권확정
      ^                            │
      └────(UC-9 시간초과 해제)─────┘

[예약]
  결제대기 ──(결제완료)──> 확정
      │
      └──(시간초과)──> ?          ← P-8에서 정할 것

[대기열 토큰]
  대기 ──(UC-10 활성화)──> 활성 ──(UC-8 결제완료 / 시간초과)──> 만료
```

> 화살표마다 물어볼 것: **누가 당기나(액터)?** / **조건은?** / **동시에 두 명이 당기면?**

## 6. 다 그린 뒤 확인할 체크리스트

- [ ] R1~R10 각각을 **어느 유스케이스의 몇 번 단계**가 책임지는지 말할 수 있다
- [ ] 시스템이 트리거하는 유스케이스(UC-9, UC-10)가 그림에 있다
- [ ] 모든 상태 전이에 "누가 / 조건 / 동시 요청 시" 답이 있다
- [ ] P-1 ~ P-10을 전부 정했다 (보류도 결정이다 — 보류라고 적기)
- [ ] 예외 흐름마다 **그때까지 바뀐 상태**를 적었다
- [ ] 각 유스케이스에 단위 테스트 1개 이상을 붙일 수 있다 (STEP03 필수 조건)
